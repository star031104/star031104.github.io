砚火 InkForge Local 开发报告：让本地 AI 真正写得动一部长篇小说

发表于2026-08-12|更新于2026-09-03|开发报告
|浏览量:

长篇小说真正困难的，从来不是生成下一段文字，而是让几百次局部生成仍然服务于同一个故事。

2026-09-03 更新：本文已按 InkForge Local v0.20 重写工程进展，补充多 Provider、Canon Lock、证据知识图谱、记忆事务、全文检索、上下文快照与真实模型验收。

大语言模型很擅长写一个漂亮的开头，也能在明确要求下完成一场对话、一段景物或一次反转。但当作品进入数十章甚至上百章以后，问题会迅速改变：人物是否还记得自己知道什么？临时衣着会不会覆盖稳定外貌？第三章埋下的线索为什么到了第三十章再也没有出现？每一卷看似在推进，是否其实只是在换一种说法重复同一套剧情？

这些问题并不主要来自“模型不会写”，而是来自系统没有为长篇叙事建立状态、约束、检查与恢复机制。这也是我开发 砚火（InkForge Local） 的起点：把本地模型从一个文本续写器，改造成一套作者可以审阅、干预和恢复的长篇生产系统。

一、项目定位：不是聊天框，而是创作工作台

砚火是一套面向中文长篇小说创作的本地优先 Web 工作台。它通过 llama.cpp 的 OpenAI 兼容接口调用本地 GGUF 模型，后端采用 FastAPI 与 SQLite，前端保持原生 HTML、CSS 和 JavaScript，尽可能降低部署门槛。

系统覆盖了从灵感到完稿的完整链路：

  1. 把一句灵感扩展为可比较的故事方向；
  2. 建立故事圣经、人物卡、世界书与全书硬规则；
  3. 生成分卷因果契约、详细蓝图和逐章路线；
  4. 为当前章节细化执行计划并生成候选草稿；
  5. 执行本地质量检查与 AI 连续性审计；
  6. 由作者确认后写入正文，并回灌长期叙事状态；
  7. 在长任务中提供暂停、恢复、重试和质量债务记录。

最重要的原则是：AI 输出先进入候选区，不直接覆盖作者手稿。 规划、正文、修订和记忆更新都保留明确的确认边界。自动化可以很深，但最终决定权始终在作者手里。

二、最核心的难题：长篇不是“更长的上下文”

最直觉的方案，是把大纲、人物、世界观和历史正文全部拼进提示词。但上下文越长，不等于模型理解得越好。无关旧信息会稀释当前任务，近似记忆会互相争夺注意力，真正关键的事实反而可能在预算裁剪中被丢掉。

因此，砚火没有把上下文当成一个大字符串，而是把它组织成一套有优先级的叙事状态：

层级负责回答的问题典型内容
作者意图这本书最终要去哪里？主题、读者承诺、终局代价、硬规则
分卷战略当前阶段必须发生什么变化？卷目标、主要场域、时间跨度、不可逆变化
章节执行这一章具体怎样推进？开篇第一拍、场景因果拍、转折、章末状态
人物与世界谁能做什么，世界允许什么？人格核心、动态状态、知识边界、世界书
叙事记忆哪些事实已经发生，依据在哪里？事实、关系、伏笔、时间线、章节结算单
写作约束这一段应怎样写，不能怎样写？末句锚点、文风指纹、描写账本、作者注

每次生成前，系统按当前人物、场景、线索和章节目标检索相关内容，并记录哪些区块被采用、估算消耗了多少 token、哪些内容因预算被裁剪。这样做的目标不是“让模型记住一切”，而是让模型在此刻记住正确的事情。

三、可追溯叙事状态：记住事实，还要记住来源

传统的“章节摘要”只能告诉模型大概发生了什么，却很难回答更严格的问题：这条信息是谁知道的？角色通过什么渠道知道？它是事实、推测还是误导？旧状态何时失效，又被什么新状态替代？

砚火把长期记忆拆成多个相互约束的账本：

  • 事实记忆：保存来源章节、正文证据、有效区间、置信状态和替代关系；
  • 人物知情：区分亲历、转述、推测与未知，避免角色获得“上帝视角”；
  • 动态关系：记录信任、敌意、信息差及关系变化的来源；
  • 伏笔生命周期：从埋设、推进、延后到可回收、已回收，同时保留目标窗口与静默债务；
  • 事件时间线：保存参与者、地点、直接前因和已经发生的后果；
  • 显著描写账本：避免人物每次出场都重复同一种外貌、动作、环境或比喻。

这套结构的价值不只是减少事实错误。它让审计拥有证据链：当模型声称某人物“早就知道真相”时，系统可以检查知识来源，而不是只凭另一轮模型调用给出一个模糊分数。

四、规划系统：把宏大纲变成可执行的因果链

很多 AI 大纲看起来完整，真正落到章节时却会退化成“遇到困难—证明方案正确—众人认可”的循环。问题在于章节只有主题，没有岗位；只有事件，没有状态变化。

砚火把规划拆为“故事骨架 → 故事圣经 → 分卷因果契约 → 逐卷详细蓝图 → 逐章路线 → 本章执行计划”。每一层只解决适合它粒度的问题。逐章路线进一步引入危机授权、首次试验、反常证据、政治阻击、修正代价、对手反制、联盟裂缝、外部后果、合法性损失、终局两难、不可逆准备与卷末兑现等剧情岗位。

岗位并不是僵硬模板，而是质量门：它要求相邻章节在叙事功能上真正不同。系统会同时比较章节目标、冲突、转折、章末变化和状态维度，拦截“换词重复”与非收束章节提前兑现卷末结果。

五、自动导演：长流程必须能够失败

本地 8B、12B 模型的现实限制很明确：速度慢、长 JSON 容易截断、偶尔断连，显存也不允许多个模型并行常驻。如果自动创作把一本书当作一次巨大调用，失败是必然的。

因此砚火的自动导演采用细粒度事务。人物卡逐张生成并立即保存；分卷契约逐卷生成；蓝图拆成梗概核心与执行清单；逐章路线每完成一章就落盘。第 N 章失败时，只从第 N 章继续，而不是重做已经通过的前 N−1 章。

系统把失败分为两类：

  • 硬故障：模型持续断开、连续超时、结构化输出多轮无法闭合。此时安全暂停，保留检查点；
  • 软质量问题：章节差异度不足、岗位偏离、计划存在可修复缺口。此时定向重写，保留最佳完整候选，并记录质量债务。

恢复任务时，系统不会盲信旧检查点，而会重新复核已保存路线，只撤回首个问题点之后的内容。这种设计背后的判断是：可靠的自动化不是永不失败，而是失败后知道从哪里继续。

六、质量系统：从单章流畅到全稿不重复

单章读起来顺畅，不代表一本书整体健康。长篇常见的问题是跨章原句复用、相似入场方式、疲劳词积累、每卷使用同一推进结构，以及历史题材中现代术语逐渐增多。

砚火采用两层质量体系：

  1. 本地确定性检查：检查长度、元话语、Markdown、未闭合标点、超长段落、重复原文、循环措辞、疑似截断和常见 AI 套话；
  2. AI 连续性审计：检查人格、声音、知识来源、关系、伤势、位置、道具、时间、世界规则和伏笔回收条件。

本地中高风险问题不会被 AI 的一句“通过”覆盖。全稿体检则进一步计算跨章段落复用、疲劳词、章节相似度、分卷阶段雷同和线索债务。自动导演遇到结构性重复会废弃候选重新起稿；只有连续系统性失败才触发质量熔断。

七、本地优先：不仅是隐私，也是产品边界

小说手稿、未公开设定和风格样文往往比普通聊天记录更敏感。砚火默认连接 127.0.0.1:8080 的 llama.cpp 服务，数据保存在本机 data/inkforge.db，不要求云端 API Key。

SQLite 使用 WAL 与写入等待保护；手动保存、接纳草稿和导演写入前都会保留章节快照；启动自动导演和删除作品前建立数据库备份；完整项目还可以导出并重新导入为独立副本。

本地优先也意味着我必须认真面对有限算力：不能依赖多个昂贵模型互相评审，不能假定请求永远快速返回，也不能把无限上下文当成工程答案。正是这些约束，推动了分段事务、确定性检查、相关性预算和安全降级等设计。

八、从 v0.16 到 v0.20：从本地写作器到可审计生产系统

v0.20 不是一次界面修补，而是一次系统边界的重画。模型接入从单一的 llama.cpp 扩展为统一的 OpenAI-Compatible Provider 层，可在本地 GGUF、SiliconFlow 与 xAI Grok 之间切换；不同供应方的地址、模型名和能力差异被收敛到同一套调用路径，凭据只在运行时使用，不进入日志、快照和导出文件。

参考资料也从“附加文本”升级为可治理的知识层。系统可以导入 TXT、Markdown、DOCX、EPUB、PDF 与 HTML，并按文风、正典、背景、研究资料分类。经过作者确认的人物档案与世界事实进入 Canon Lock，生成前由 Canon Gate 检查冲突，生成后再执行 OOC 与连续性审计。知识条目保留证据、来源和替代关系，因此系统知道什么是当前有效状态，也知道旧状态为什么失效。

章节接纳流程新增了记忆完整性事务：正文与结算结果以 SHA-256 绑定，证据验证通过后才提交长期状态；如果回灌失败，章节会进入 settlement_pending 或 state_degraded，而不是伪装成一次完整成功。旧正文通过 SQLite FTS5 参与检索，同时显式区分作者、读者和角色各自能够知道的信息，减少跨视角泄漏。

为了让一次生成可以被解释和复现，v0.20 会保存脱敏后的提示词与上下文快照，记录检索片段、预算裁剪和模型参数，并支持重放。写作 Skills 只能提供受控的写作策略，不能执行外部工具，也不能覆盖正典事实。工程验收不再停留在模拟调用：除了本地自动化测试，还完成了 SiliconFlow 真实模型链路与百章规模创作资产验证。

九、技术实现与当前状态

模块技术职责
Web APIFastAPI + Uvicorn项目管理、流式生成与长任务接口
模型通信HTTPX + OpenAI-Compatible ProviderSiliconFlow、xAI Grok 与 llama.cpp 的统一流式调用
数据模型Pydantic请求、规划和结构化输出校验
持久化SQLite / WAL作品、章节、记忆、快照和任务状态
前端原生 HTML / CSS / JavaScript本地写作工作台与流式交互
测试PytestAPI、规划、记忆、质量与恢复验证

当前版本为 v0.20.0，测试基线为 231 项全部通过，Python 编译检查与前端 JavaScript 语法检查也已通过。项目仍然有明确边界：文风学习是 RAG 与提示词层的软学习，不是 LoRA；token 是估算值；连续性审计能降低错误但不能替代作者判断；本地规则可以发现机械问题，却不能评价一部小说的文学价值。

十、回看这次开发：真正重要的是控制权

开发砚火之后，我越来越确信：AI 写作工具的竞争力，不应只用“单次能生成多少字”衡量。对长篇创作而言，更关键的是它能否解释自己使用了哪些记忆，能否在失败后恢复，能否发现结构性重复，能否把修改限制在候选稿，以及能否让作者随时接管。

模型能力会继续提升，但小说创作依然需要方向、取舍与审美。工具应该承担的是那些最消耗注意力、最适合结构化管理的工作：整理状态、维护证据、检查连续性、记录历史、提示债务，并把复杂流程变成可回退的步骤。

让模型记住故事，让作者掌握方向。

这就是“砚火”这个名字想表达的东西：砚是容器，是秩序，是长久保存的痕迹；火是生成，是变化，是每一次落笔之前尚未确定的可能。
