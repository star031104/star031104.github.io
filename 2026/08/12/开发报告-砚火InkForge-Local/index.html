砚火 InkForge Local 完整开发报告：从创作困境到本地 AI 长篇生产系统

发表于2026-08-12|更新于2026-09-26|开发报告
|浏览量:

AI 很容易写出一个漂亮的开头，却很难陪作者稳定地完成一部长篇小说。

我最初思考这个项目时，关注的并不是“怎样让模型一次生成更多文字”，而是另一个更实际的问题：当创作进入十章、三十章甚至更长的尺度以后，怎样让人物仍然记得自己知道什么，让关系变化有前因，让伏笔按计划推进，让作者修改前文之后，系统知道哪些后续记忆已经不再可信？

这些问题最终变成了 砚火（InkForge Local）。它是一套面向中文长篇与同人创作的本地 AI 写作工作台，也是一场关于“怎样把生成式模型变成可靠创作系统”的工程实践。

这篇文章不只介绍最终功能。我想完整记录它为什么出现、最初的灵感是什么、我如何定义问题、为什么选择现在的技术路线，以及它怎样从一个写作页面逐步发展成包含规划、正文、审校、记忆、恢复与部署的完整系统。

项目地址：GitHub · InkForge Local

最新版本：InkForge Local Releases

一、项目的起点：我想解决的不是“生成”，而是“完成”

在大模型刚开始进入写作场景时，最直观的用法是把设定和前文发给模型，让它续写下一段。这个过程在短篇、片段练习和灵感探索中非常有效：模型反应快，表达流畅，也经常能够给出意料之外的转折。

但只要尝试把这种方式延伸到长篇，体验就会迅速发生变化。

  • 模型记得人物名字，却忘了人物为什么做出某个选择；
  • 它读过世界观，却会把未经确认的推测当成事实；
  • 它知道上一章发生了什么，却可能让角色提前知道尚未公开的信息；
  • 大纲看起来完整，拆成章节后却反复出现同一种冲突；
  • 局部重写了早期章节，旧摘要和旧人物状态仍然继续污染后文；
  • 一次长任务超时，前面已经完成的规划也可能全部丢失；
  • 自动“精修”看似完成，实际上只是生成了新文字，并没有证明问题真正解决。

我逐渐意识到，长篇小说的难点不是字符数量，而是状态随时间持续变化。人物、关系、地点、伤势、道具、知识、伏笔和读者信息都在变化，而且每一次变化都应该能够追溯到具体正文。

因此，这个项目最早的核心命题并不是“做一个 AI 小说生成器”，而是：

能不能做一套系统，让 AI 参与整部长篇的生产，同时让每一步都能够检查、恢复、修改和追溯？

这也决定了砚火后来最重要的产品方向：它不会把小说当成一条连续文本，而会把它当成一个长期运行、不断演化的创作工程。

二、名字与灵感：砚负责承载，火负责生成

“砚火”这个名字来自我对这套工具的两个期待。

砚代表承载、秩序和长期留下的痕迹。小说中的设定、人物状态、证据、历史版本和作者决定都需要被稳妥保存。系统不能只记得模型最后一次说了什么，更要知道某条信息从哪里来、何时生效、何时失效。

火代表生成、变化和创作中的不确定性。模型的价值恰恰在于它能够提出作者尚未想到的方向，补充场景细节，模拟不同人物的反应，并在约束之内带来新的可能。

只有“火”而没有“砚”，生成会越来越失控；只有“砚”而没有“火”，系统又会退化成繁琐的资料管理工具。这个名字后来也成为架构设计的一条线索：一边允许模型自由生成候选内容，一边用结构化状态、证据和版本机制承接它。

三、立项时确定的目标：让作者从一句灵感走到完整手稿

明确问题之后，我把理想中的完整流程画成了一条创作链：

它必须同时满足两类用户。第一类作者已经有明确设定，需要工具帮助管理大纲、章节和连续性；第二类作者只有一句模糊灵感，希望 AI 协助完成作品定位、人物、世界和整体规划。前者需要控制感，后者需要引导感，所以系统既要支持手动逐步创作，也要支持从灵感开始的自动导演流程。

我为项目确定了五条基本原则。

  1. 作者拥有最终决定权。 AI 输出先成为候选稿，不能静默覆盖已经确认的正文。
  2. 作品事实必须有来源。 模型说过的话不等于故事中已经发生的事实。
  3. 长任务必须可以失败。 可靠不是永远不出错，而是出错后知道从哪里继续。
  4. 本地数据优先。 正文、设定、历史和凭据应该由作者掌握。
  5. 模型是可替换能力。 作品不能绑定某一家供应商或某一个模型。

这些原则比某一个具体功能更重要。后来的数据库设计、候选稿机制、模型路由和自动部署，实际上都是它们的延伸。

四、把想法变成需求：一套长篇系统究竟要做什么

立项初期最容易犯的错误，是一开始就堆叠按钮。我先把长篇创作拆成若干责任明确的子系统，再决定界面应该出现什么。

4.1 创作与编辑

最基础的能力包括新建作品、章节管理、正文编辑、续写、按要求创作、选区重写和扩写。生成结果需要进入独立候选区，作者能够比较修改前后内容，选择采用、局部采用或放弃。

4.2 故事规划

系统需要把一句灵感扩展为两套可以比较的开书方案，再建立主题命题、读者承诺、故事发动机、贯穿冲突和终局代价。全书规划继续拆成分卷蓝图、逐章路线和本章执行计划，确保不同层级只解决适合自己的问题。

4.3 人物、世界与资料

人物卡不仅要保存稳定人格和外貌，也要区分临时状态。世界书需要按关键词、条件和作用域触发。参考资料要区分文风样文、原作正典、世界背景和研究资料，避免“学习文风”和“确认事实”互相污染。

4.4 连续性与长期记忆

系统需要维护事实、人物知情、动态关系、事件时间线和伏笔生命周期，并且记录对应章节与正文证据。修改已结算章节以后，依赖旧正文产生的后续记忆必须失效，而不是继续作为可信上下文。

4.5 审校与精修

质量检查既要覆盖长度、截断、重复、套话等确定性问题，也要覆盖人格、声音、知识来源、关系、地点、时间和世界规则等语义问题。精修不能只是重新生成一遍，而应该经历“检查—修订—复检—接纳”的闭环。

4.6 自动导演

如果用户希望由 AI 完成大部分流程，系统需要自动完成开书、规划、拆章、正文、审校、修订和记忆回灌。整个过程必须显示阶段、进度、日志和失败原因，并支持暂停、恢复与从检查点继续。

4.7 部署与数据保护

普通用户不应该先学会 Python 和虚拟环境才能写小说。项目需要有可以双击启动的 Windows 入口，同时处理依赖安装、日志、端口、数据目录、升级和备份。

五、技术选型：为什么选择 FastAPI、SQLite 和原生前端

项目最终采用 FastAPI、Pydantic、SQLite、HTTPX 和原生 HTML/CSS/JavaScript。

选择 FastAPI，是因为项目包含大量结构化请求、流式生成和后台任务。类型明确的请求模型能尽早拦截不完整输入，异步接口也适合模型流式响应。Pydantic 则承担了规划对象、审校结果和模型结构化输出的验证。

选择 SQLite，是因为砚火本质上是本地单机创作工具。它不需要用户维护数据库服务，却仍然能够提供事务、索引、并发写入保护、FTS5 全文检索和可验证备份。WAL 模式减少读取和后台写入之间的阻塞，版本表与迁移机制则保证旧作品能够继续打开。

前端保持 原生 JavaScript，是为了让源码、便携版和自动部署版共享同一套静态资源，不增加复杂构建链。随着功能变多，前端后来拆分成项目、生成、规划、资料、审校、治理、自动导演和场景工具等模块，但仍然保留轻量、可离线运行的特点。

模型通信统一使用 OpenAI-Compatible HTTP/SSE 协议。这样一来，智谱、ModelScope、本地 llama.cpp 和其他兼容服务都能够通过同一个 Provider 层接入，业务逻辑不需要理解每一家供应商的差异。

六、第一次实现：先完成一个能写作的最小闭环

第一阶段并没有直接挑战“自动完成整本小说”。我先实现最小的可用闭环：创建作品、编辑章节、调用模型生成候选正文、由作者接纳，然后保存。

这个阶段验证了三件事。

第一，流式输出对于写作体验非常重要。等待模型生成数千字时，如果界面没有任何反馈，用户很难判断程序是否卡住。第二，候选稿必须与正文分离，否则一次错误生成就可能破坏手稿。第三，每个模型任务需要不同提示词，续写、重写选区、扩写和新章生成不能共用同一种上下文配方。

最小闭环稳定后，我才继续向规划和长期记忆扩展。这个顺序避免了系统在没有可靠写入边界时就拥有过强的自动化权限。

七、规划系统：从宏大纲变成可执行路线

AI 生成大纲的常见问题不是缺少事件，而是事件之间没有不可替代的因果职责。很多章节只是换了地点和角色，实际仍在重复“遇到问题—展示能力—获得认可”。

为了解决这一点，我把规划拆成多层结构。

  • 故事骨架决定主角起点、核心缺口、主要压力和最终变化；
  • 故事圣经固定主题、读者承诺、故事发动机和终局代价；
  • 分卷蓝图规定每一卷的场域、时间跨度、主要选择和不可逆变化；
  • 逐章路线要求每章拥有独立目标、冲突、转折和章末状态；
  • 本章计划进一步细化到场景入口、阻力、变化与退出状态。

系统会检查相邻章节的职责与结果是否过于相似，并允许作者选择因果与人物、悬疑、关系、冒险、观察或自定义叙事策略。经典的十二岗位模式仍然保留，但它只是可选方法，不再成为所有故事的硬模板。

批量建章遵循小批次事务。模型每完成一组章节就立即保存，通过验证后再继续下一组。这样既降低结构化输出被截断的概率，也使失败恢复成为可能。

八、最关键的重构：把摘要记忆升级为证据记忆

早期版本和许多写作工具一样，依赖章节摘要维持上下文。摘要很方便，却存在一个根本缺陷：它会不断把模型的解释压缩成新的“事实”，而原始依据逐渐消失。

因此，长期记忆后来被重构为带证据的状态系统。

每一条事实、人物状态、知情、关系变化和伏笔更新，都要绑定来源章节、正文片段与正文 SHA-256。模型可以提出候选状态，但只有证据能够在正文中找到，并通过本地校验后，它才会进入权威记忆。

这个机制解决了几个长期问题。

  • 同一正文反复结算不会生成重复事实；
  • 正文改变后，旧结算结果不能再次提交；
  • 修改早期章节会让相关后续记忆失效；
  • 系统能够区分永久人物核心和临时场景状态；
  • 生成当前章节时可以排除当前章与未来章节的动态信息；
  • 作者真相、读者已见内容和人物有证据知情可以分别编译。

全文检索只是可重建的投影，作品 JSON 始终是事实源。检索结果还要经过类型配额和相似内容抑制，避免大量同类旧正文挤掉世界规则或当前人物状态。

九、同人创作为什么需要 Canon Lock

同人小说对角色一致性的要求比普通原创更复杂。作者不仅要保持自己作品内部的连续性，还要处理原作时间点、人格、能力边界和说话方式。

为此，我实现了 Canon Profile 和 Canon Gate。

Canon Profile 保存原作、时间节点、人格核心、价值观、能力限制、语言模式、行为模式、情绪模式和禁止 OOC 清单。AI 可以根据上传资料生成待核对档案，但未经人工确认的结论不会成为最高级约束。

Canon Gate 在正文接纳前检查明显 OOC、无铺垫关系突变和高风险样文复刻。资料中的事实、模型推断和争议解释分别保存，证据必须能够回到具体来源。这里最重要的不是让系统假装自己“懂原作”，而是让它诚实地区分知道、推断和不知道。

十、自动创作与精修：让长流程能够中断和恢复

“一键创作全文”听起来像一个按钮，实际是整套系统中最复杂的工作流。它包含作品设定、人物、全书规划、分卷、拆章、逐章正文、审校、修订和记忆结算。任何一步都可能超时、断连或返回不完整结构。

我的实现方式不是让一个巨大请求承担所有工作，而是把流程拆成可持久化的阶段任务。每个阶段完成后写入 SQLite 检查点，记录当前作品、章节、状态、进度、日志和可恢复位置。

关闭浏览器不会结束任务，因为任务运行在本地服务中。重新打开后，界面从数据库读取真实状态，而不是依赖页面内存中的进度条。服务重启时，系统也会识别失去租约的任务并转为可恢复状态。

AI 自动精修同样采用闭环：先审校，再生成整章修订候选，随后重新审校并执行硬规则扫描。达到目标后才能接纳；没有通过的版本留在检查点中，不覆盖原正文。发布门禁、连续性复核和文学判断被分开呈现，避免一个模糊总分掩盖具体风险。

十一、模型设置的演化：从厂商名称回到用户选择

早期界面容易把“单模型”“双模型”和特定模型名称混在一起，用户需要理解内部路由才能完成设置。后来的重构把它简化为真正的产品语言：使用一个模型，或使用两个模型。

一个模型时，所有任务使用同一配置。两个模型时，模型 1 主要负责正文、续写和修订，模型 2 主要负责规划、审校和信息提取。两边都有有效 Key 时自动分工；只有一边可用时，全部任务自动回退到可用模型。本地 llama.cpp 不要求 Key。

这种设计让模型成为可替换的能力，而不是作品结构的一部分。作者可以更换 Provider，但人物、规划、正文、记忆和审计历史不会随模型一起消失。

十二、从功能项目到工程项目：v0.33.1 的整体重构

功能不断增加以后，新的问题出现了：入口文件越来越庞大，HTTP 路由、故事规则、数据库和后台任务相互调用；前端脚本也开始共享过多隐式状态。项目虽然能运行，却很难继续安全扩展。

因此，v0.33.1 进行了一次完整的工程化重构。

后端被拆分为清晰的层次：

  • app/api 负责请求验证、状态码和协议；
  • app/domain 保存无 I/O 的规划、正文和路线规则；
  • app/services 编排结构化输出、记忆结算和自动导演；
  • app/infrastructure 负责检索、凭据、进程锁和周期备份；
  • app/entrypoints 统一源码、便携版和启动器的运行入口。

前端也按项目、生成、规划、资料、审校、治理、自动导演和场景工作台拆分。入口只负责绑定事件，功能脚本各自维护明确职责。

数据一致性方面，保存使用作品版本进行乐观并发控制。另一个窗口或后台任务更新作品后，旧页面不能静默覆盖新内容。章节接纳、记忆结算和检索更新放在受控事务中，模型凭据则进入独立 secrets 数据库，不进入作品历史、提示词快照或 JSON 导出。

Windows 上的 Key 使用当前用户 DPAPI 加密。自动备份跟随应用生命周期运行，恢复前先创建安全快照，校验或恢复失败时自动回滚。

十三、部署实现：双击之后自动准备环境

如果项目只能通过终端运行，它就仍然只是开发者工具。为降低使用门槛，我为 Windows 编写了独立自举启动器。

用户下载自动部署包后，只需要解压并双击 InkForgeLauncher.exe。启动器会检查 Python 与依赖环境；缺失时从固定的 Python 官方地址下载安装包并校验 SHA-256，然后建立与应用版本和依赖指纹绑定的隔离环境。准备完成后，它会启动本地服务、等待健康检查通过并打开浏览器。

依赖缓存完整后可以离线复用。作品数据库、凭据、日志和备份都位于当前用户数据目录，更新或重新解压程序不会覆盖小说。

项目同时提供完整便携版，适合离线保存和固定运行环境；源码用户仍可通过 run.bat 或 run.ps1 启动。三种方式最终进入同一个服务入口，避免不同发行方式出现不一致行为。

十四、完整的实现流程回顾

把整个开发过程压缩成一条路线，大致经历了以下阶段。

  1. **验证最小写作闭环：**作品、章节、流式生成、候选稿和安全接纳。
  2. **建立分层规划：**从故事骨架到分卷、逐章和场景执行计划。
  3. **引入结构化记忆：**事实、知情、关系、时间线与伏笔。
  4. **补充质量体系：**确定性检查、AI 连续性审计和全稿级重复分析。
  5. **实现自动导演：**把长流程拆成可持久化阶段与检查点。
  6. **加入 Canon 与资料治理：**让同人角色和外部资料拥有证据边界。
  7. **统一模型路由：**支持单模型、双模型和多个兼容 Provider。
  8. **处理真实并发与恢复：**版本冲突、任务租约、正文哈希和备份回滚。
  9. **重构工程边界：**拆分 API、领域、服务、基础设施和前端模块。
  10. **完成桌面部署：**便携包、自举启动器、版本契约和发布检查。

这条路线并不是一开始就被完整设计出来的。很多结构是在真实问题出现后逐渐形成：页面关闭后进度消失，促使任务状态进入数据库；自动精修“完成”却没有真正通过门禁，促使修订和复检分离；双模型设置难以理解，促使界面回到一个模型或两个模型的简单选择；早期正文修改污染后文，最终促成证据记忆与失效重建。

对我来说，这也是项目开发最有价值的部分：问题不是通过增加更多提示词解决，而是通过重新划定系统责任解决。

十五、测试与发布：怎样证明它不仅是“能打开”

AI 产品的演示通常展示一次成功结果，但工程系统必须处理失败、重试和不完整输出。砚火的验证覆盖领域规则、项目版本、数据库迁移、任务检查点、记忆事务、模型传输、静态资源与发布契约。

v0.33.1 发布时完成了：

  • 69 项自动化测试；
  • 13/13 离线质量评估；
  • 11 个前端脚本语法检查；
  • Windows、Linux 与 Python 3.10、3.12 的组合 CI；
  • 自动部署版和便携版的启动、健康检查与环境准备验证。

项目还提供真实模型验收运行器，用隔离数据库验证单模型、双模型、多章连续创作，以及服务被强制终止后的恢复。验收报告自动脱敏，不保存 Key。

这些检查不能判断一章小说是否真正动人，但可以守住工程底线：正文不能凭空丢失，任务必须能够恢复，事实需要证据，未来信息不能提前泄漏，模型异常不能静默破坏已确认内容。

十六、当前边界与下一步

砚火现在已经形成了从灵感到全文、从候选稿到审校精修、从正文证据到长期记忆的完整闭环，但它仍然有清晰边界。

文风学习是 RAG 与提示词层的软学习，不是模型微调；token 数仍然是本地估算；连续性审计能够降低事实错误，却不能替代作者对关键设定的确认；本地规则擅长发现机械问题，但不能评价主题深度和文学价值。不同模型的中文表达、结构化输出和长上下文能力也会直接影响最终效果。

后续工作仍会围绕三个方向展开：让上下文选择更准确，让自动创作过程更透明，让本地部署和版本升级更轻松。

十七、最后的复盘：AI 写作工具真正应该帮助作者什么

完成这次重构后，我对 AI 写作工具的理解也发生了变化。

真正消耗作者精力的，不只是把一句话扩展成一段文字，而是长期维护作品的复杂性：人物为什么做出这个选择，某条信息从哪里来，谁在什么时候知道了什么，一次修改影响到哪些后文，以及模型生成的内容是否值得成为正式手稿。

因此，砚火追求的不是让作者退出创作，而是把最适合结构化管理的工作交给系统：整理状态、维护证据、检查连续性、记录历史、提示风险，并把复杂流程变成可以暂停、恢复和回退的步骤。

模型负责提供可能性，系统负责保存秩序，作者负责决定作品最终成为怎样的故事。

这就是砚火从最初灵感到 v0.33.1 的完整开发过程，也是我希望它继续坚持的方向。
