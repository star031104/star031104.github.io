映章 YingZhang：从材料到可编辑演示的 AI PPT 生产系统

真正困难的不是让模型“写十页 PPT”，而是让证据、叙事、视觉、人工选择和最终交付在同一条可恢复工作流里保持一致。

浅梦 · 发布于 2026-09-04 · 更新于 2026-09-05 · 约 18 分钟阅读

现在的模型已经能快速生成大纲和文案，但一份真正要交给客户、老师或管理层的演示，不只是一组文字卡片。它必须回答：数字来自哪里？为什么这一页用图表而不是列表？修改一页时能不能保住其他页面？导出的 PowerPoint 是否仍然可编辑？任务中断后能否继续？

映章的目标不是替人“按一下生成 PPT”，而是把专业演示生产拆成可计划、可检查、可修复、可交付的工程流程。

一、项目定位：生成器之外，更像一间演示工作室

映章是一套中文优先的智能演示创作系统。输入可以是一段主题说明，也可以是 PDF、Word、Excel、PPT、Markdown、网页或图片材料；输出则覆盖 HTML 预览、PDF 与原生可编辑 PPTX。

系统在生成前明确受众、沟通目标、演讲时长、语气和品牌，再把材料解析、证据提取、叙事规划、页面拆解、候选渲染、视觉检查与导出串起来。人工可以在关键节点选择版式、编辑对象、批准版本，而不是只能接受模型给出的唯一答案。

二、核心方法：先建立证据与契约，再生成页面

传统链路通常是“用户提示词 → 大模型 → PPT 文件”。它足够短，却会把事实可靠性、版式决策和错误恢复都塞进一次不可观察的调用里。映章采用分层流水线：

材料导入 ↓ 解析、切分、来源登记 证据图谱 ↓ 受众 / 目标 / 叙事 / 页面角色 演示计划 ↓ 页面契约、文字预算、对象上限 候选渲染（页级并发） ↓ 几何 / 可读性 / 层级 / 语义检查 定向修复与人工选择 ↓ HTML · PDF · 原生可编辑 PPTX

每个节点都声明输入、输出、幂等键、重试范围和产物位置。于是“恢复任务”不是重新猜一遍模型当时在做什么，而是复用已经完成且仍然有效的节点。

三、证据约束：把“看起来可信”变成“可以追溯”

映章会把材料中的数字、结论、原文图和来源章节绑定到页面。观众页脚保持干净，精确出处、讲解要点与过渡语进入演讲备注。重要章节还会经过语义完整性检查，避免系统仅仅“挂了一个引用”，却没有真正覆盖材料的关键结论。

开放网络素材也不是搜到就用：图片需要登记作者、许可、来源链接和替代文本，许可不明确的候选不能进入最终页面。这套台账同时服务于版权复核和无障碍交付。

四、视觉生成：候选、选择、反思，而非一次押注

多候选

每页生成 3–5 个真实渲染候选，按页面角色、内容负载、证据类型和全稿节奏评分。

语义路由

多指标优先图表，过程优先流程，差异优先对比，主张页控制对象数量与文字预算。

视觉反思

截图后检查溢出、碰撞、留白、层级、焦点和相邻页面同构，只做有边界的定向修复。

人工边界

用户选中的版式和完成的手工修改被锁定，后台重试不会悄悄覆盖已经确认的结果。

这种模式借鉴了优秀 AI 演示项目中“规划—生成—渲染—评价”的思想，也吸收了 ai-ppt-generator 对工作流编排和演示生成的实践，但实现上并未机械复制：映章进一步加入了页级并发、持久化任务、有界节点、证据图谱、对象级编辑和多格式一致交付。

五、任务系统：长流程必须能取消、恢复和追踪

生成整套演示是长任务。映章把任务存储、执行器和实时事件拆成独立契约，本机默认可以零外部依赖运行，同时为 PostgreSQL、Redis 和分布式队列保留稳定接入边界。

  • 大纲、样张、整稿与单页任务都保存上下文和节点进度；
  • 服务重启后可重新入队，不必丢弃全部成果；
  • 前端通过带首帧快照与心跳的事件流接收进度，断线时自动降级轮询；
  • 取消发生在安全步骤边界，单页失败不会阻断其他页面；
  • 正文、对象、候选与画布布局使用版本号拒绝过期写入。

六、编辑与交付：最终文件必须继续工作

系统支持页内对象级对话编辑：可以只改标题、某条要点、图表或视觉对象；也可以只重新生成当前页。所有修改保留消息记录和页面版本，并一致进入 HTML、PDF 与 PPTX。

PPTX 不是截图容器。数据表、时间线、流程、分层架构和关系图优先输出为 PowerPoint 原生对象；企业模板通过页面角色选择母版；演讲备注、转场、动画、旁白以及图片、音视频也有明确的交付路径。对既有 PPTX，系统还能局部改写页面对象，同时尽量保留主题、母版、版式和动画结构。

七、工程优化：让复杂系统仍然可以维护

随着能力增长，最初集中的工作流入口容易变成难以维护的“大文件”。本轮优化按领域拆分项目、生成、审阅、发布、品牌、素材和 PowerPoint 等路由，同时保留清晰的装配边界。生成引擎与前端工作台也分别收敛到更可测试的模块。

当前自动验证覆盖 79 项后端测试、23 项生成引擎测试和 2 项前端测试；前端生产构建通过，101 个接口方法与路径组合无重复。这些数字不是完成的终点，却证明核心边界已经能够被持续验证。

八、从参考项目吸收什么，又放弃什么

这次实现系统研究了 yuyuanweb/ai-ppt-generator。它最有价值的地方，不是某一个模板，而是把演示生成理解为规划、内容生产、页面渲染和结果检查共同组成的流程。这个认识决定了映章不会把全部责任交给一个超长提示词。

参考思想映章的吸收与扩展
先规划再生成增加受众、目标、叙事节奏、逐页证据和构图契约
页面生成需要渲染反馈增加真实截图评分、视觉基线、相邻同构检测和有界修复
工作流节点化为节点补充 Schema、幂等键、重试白名单、最大次数和产物路径
多种页面形态按语义路由图表、流程、关系、对比和主张页，并约束全稿节奏
演示文件导出统一 HTML、PDF、可编辑 PPTX，并支持企业模板与既有 PPTX 续编

没有直接照搬的部分也同样重要。映章没有把模板数量当成视觉质量，没有让模型自由执行外部代码，也没有允许一次失败无限重试。专业系统需要明确知道哪里可以创造、哪里必须保守、哪里一定要由人确认。

九、这套框架最值得保留的思想

  • 演示是叙事产品，不是页面集合。先确定受众、目标和节奏，再决定每页内容。
  • 模型输出是候选，不是事实。证据、许可、质量门禁和人工批准必须有独立位置。
  • 视觉需要闭环。只生成代码无法知道画面是否成立，必须真实渲染并检查。
  • 长任务必须有状态。恢复、取消、重试和并发冲突不是附加功能，而是生产系统的基础。
  • 交付物要可继续编辑。真正有价值的 PPTX 应当进入团队后续工作，而不是结束于一张张图片。

十、技术架构：本地优先，但边界可替换

后端使用 FastAPI、SQLAlchemy、SQLite 与 Alembic，负责项目、来源、页面、版本、任务、审阅和发布；前端使用 React 19、TypeScript、TanStack Query 与 Zustand，负责创建、进度、候选选择、画布编辑和质量工作台；生成引擎以 Playwright 完成真实浏览器渲染，再通过 PptxGenJS 与 python-pptx 生成和续编 PowerPoint。

React 创作工作台 ├─ 项目 / 材料 / 大纲 ├─ 页面候选 / 画布 / 对象编辑 └─ 质量 / 审批 / 发布 ↓ 同源 API FastAPI 领域服务 ├─ Source + Evidence ├─ Planning + Art Direction ├─ Bounded Workflow Nodes ├─ JobStore + Executor + EventBus └─ Quality + Governance + Delivery ↓ SQLite / 本地产物 / Chromium / PPTX

默认实现保持本机零外部依赖，便于个人使用和快速验证；任务存储、执行器与事件总线通过契约隔离，为未来替换 PostgreSQL、Redis、对象存储和分布式队列留下稳定边界。

十一、公开测试：先验证真实工作流，而不是追求虚假在线

映章已经提供受邀测试模式：测试者通过姓名与密码登录，管理员与普通测试者权限分离；写操作执行同源校验，并限制登录频率、请求频率、生成频率和上传大小。模型配置、技能安装等高风险入口只对管理员开放。

当前没有自有域名，因此测试环境通过 Cloudflare Quick Tunnel 将本机服务映射到随机的 trycloudflare.com HTTPS 地址。Cloudflare Quick Tunnel 不支持 SSE，前端会在事件连接失败后自动切换为轮询，所以生成能力仍可使用，只是进度刷新不如固定隧道实时。

这是一轮小范围邀请测试：电脑关机、休眠、断网或重启隧道都会使地址失效；测试者应使用虚构或脱敏材料，公开地址不应附带管理员密码传播。

十三、当前边界与下一步

  • 多人隔离：当前公开模式适合小范围邀请，尚未完成严格的租户级项目隔离。
  • 持续在线：本机和随机隧道不提供生产 SLA，后续需要云主机、外部数据库和对象存储。
  • 视觉上限：自动评分能发现确定性问题，但不能取代人对审美、业务表达和现场讲述的判断。
  • 格式兼容：跨 PowerPoint、WPS 与 LibreOffice 的字体和媒体表现仍需在目标环境预检。
  • 成本控制：模型调用、图片搜索和页面候选深度需要按照测试人数持续衡量。

下一阶段会优先收集真实用户在哪些页面反复修改、哪些候选被选中、哪些交付失败，再决定是否扩大模板、接入远程任务基础设施或提供正式托管版本。比起堆叠功能，这些数据更能告诉系统离“专业”还差在哪里。
