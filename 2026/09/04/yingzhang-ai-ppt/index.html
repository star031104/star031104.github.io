映章 YingZhang 开发报告：让 AI 演示从生成走向可交付

发表于2026-09-04|更新于2026-09-14|开发报告
|浏览量:

做 AI PPT 这件事，最容易得到的是“几页看起来像幻灯片的内容”，最难得到的却是一个真正能够交付的文件。

当输入只是一句话时，模型可以很快给出标题、要点和配图建议。但真实工作里的输入往往是一组 Word、PDF、Excel、旧演示稿和网页资料。它们包含相互依赖的数据、结论、限制条件与图表。系统不仅要决定讲什么，还要说明依据来自哪里、为什么这样组织，以及最终导出的 PPTX 是否还能继续编辑。

这也是我开发映章（YingZhang）的起点：不再把 PPT 生成理解为一次提示词调用，而是把它拆成材料理解、证据组织、叙事规划、页面生成、质量检查、人工确认和正式导出等一系列可以检查的步骤。

2026-09-14 更新：映章已发布首个公开版本 v0.1.0。公开仓库从一条独立的根提交开始，不承接此前内部开发历史；仓库中不包含维护者的 API Key、本地路径、个人偏好、运行数据或版本历史文档。

一、项目定位：不是自动排版器，而是演示生产工作台

映章是一套中文优先、本地运行的 AI 演示生产系统。它面向的不是“输入一句话，随机生成几张模板页”，而是需要阅读材料、建立论证、反复修改并最终交付的真实任务，例如课程汇报、毕业答辩、研究报告、产品方案和业务复盘。

整个系统围绕五个原则设计：

  • 材料先于文案：先理解用户提供的文件，再决定演示中应该出现哪些信息；
  • 证据先于结论：数字、判断和图表尽量保留来源位置与适用边界；
  • 结构先于装饰：先确定受众、目标和叙事顺序，再选择页面布局；
  • 候选先于覆盖：AI 生成的内容先进入候选区，由用户选择后再进入正式版本；
  • 交付先于预览：网页中好看只是中间状态，最终还要得到可复核、可修改的 PPTX。

因此，映章更像一个演示项目的工作台。用户可以看到材料是否被正确读取、大纲为什么这样安排、某页引用了哪些信息、页面为什么没有通过检查，以及修改之后应该重新生成整套演示还是只修复当前页面。

二、整体架构：把一次生成拆成四层职责

首版采用前后端分离的结构，但正式运行时可以由 FastAPI 统一提供前端页面和 API。这样既方便本地一键启动，也保留了前后端独立开发的空间。

层级主要技术负责的事情
创作工作台React 19、TypeScript、Vite项目创建、材料上传、大纲审阅、页面候选、质量结果和导出操作
API 与工作流FastAPI、Pydantic、SQLAlchemy任务编排、状态保存、模型调用、失败恢复和接口校验
文档与演示引擎PyMuPDF、python-docx、openpyxl、Playwright、PptxGenJS材料解析、网页渲染、PDF 输出和可编辑 PPTX 生成
本地数据与配置SQLite、系统密钥环、文件存储项目、证据、页面版本、生成产物与模型凭据

三、材料理解：读取文件不等于理解文件

普通的文本提取只能得到一串字符，但演示生产真正需要的是结构。例如，一个数字属于哪一年的哪项指标，表格中的单位是什么，结论是在正文里明确给出的，还是由模型推测得到的。

映章目前可以处理 PDF、DOCX、XLSX、CSV、PPTX、Markdown、HTML 和常见图片格式。解析阶段会尽可能保留下列信息：

  • 文档标题、章节层级和段落顺序；
  • 表格的行列关系、单位、表头和计算值；
  • 图片、图表与它们在原文中的上下文；
  • 关键数字、结论、限制条件和来源位置；
  • 扫描文档、缺失公式结果或内容截断等风险。

解析结果不会直接变成幻灯片文案，而是先进入证据层。每条准备进入演示的主张，都可以关联到原始文件、章节或表格区域。这样做虽然比“把全文扔进提示词”更慢，但能够显著减少数字失真和断章取义。

四、叙事规划：先回答为什么讲，再决定每页讲什么

同一组材料，面对老师、客户或项目组时，应该得到完全不同的讲法。页数也不能简单按材料长度平均分配，因为背景、问题、证据和结论在不同场景中的权重并不相同。

创建项目时，映章会先收集受众、演示目标、预计时长、语言、语气、品牌要求和输出比例。随后生成演示级叙事结构，再把它拆成逐页计划。

每一页不是只有一个标题，而是有一份页面契约，主要包括：

  • 这一页在整套演示中的角色；
  • 希望观众记住的核心主张；
  • 支撑主张的证据及其来源；
  • 适合采用的数据图、时间线、流程或对比关系；
  • 文字预算、对象数量和版面限制；
  • 与前后页面之间的承接关系。

页面契约把“写内容”和“做版式”之间的责任分开。模型可以提出视觉方案，但不能为了排版方便擅自删掉必要证据，也不能把一个限定性结论改写成绝对判断。

五、页面生成：候选、检查和修复是三个阶段

页面生成没有采用“一次生成，直接定稿”的方式。对于重要页面，系统可以根据同一份页面契约生成多个候选，再从信息完整性、可读性、视觉层级和布局风险等角度进行比较。

检查主要分成三类：

检查类型典型问题处理方式
内容完整性关键结论缺失、数字与来源不一致、限定条件被省略回到证据或页面契约重新生成内容
视觉质量文字溢出、字号过小、对齐异常、对比度不足只调整受影响对象或重新选择布局
交付风险字体替换、外部素材许可、Office 渲染差异给出提示并在目标环境中复核

用户选定某个候选后，该选择会受到保护。后续如果只修改一个数字或标题，系统应尽量局部修复，而不是重新生成整页并破坏已经确认的布局。

长任务也被拆成有界步骤。某一页失败时，可以从该页继续；模型超时或渲染中断时，已经完成并通过检查的页面不需要全部重做。这一点对十几页以上的演示尤其重要。

六、交付格式：网页预览只是中间结果

映章可以输出 HTML、PDF 和 PPTX。HTML 适合快速预览，PDF 适合固定版式，而 PPTX 才是多数演示任务真正需要继续修改和现场播放的格式。

首版在导出 PPTX 时，优先把以下内容保留为原生对象：

  • 标题、正文、标签和注释等文本框；
  • 柱状图、折线图和饼图等常见图表；
  • 数据表、时间线、流程图、层级图和关系图；
  • 基础形状、分隔线、背景区域和页面编号。

这意味着用户可以在 PowerPoint 或 WPS 中继续改字、换色、移动对象，而不是拿到一张铺满整页的截图。图片和复杂视觉仍可能以位图或 SVG 形式进入文件，但正文结构不会为了“看起来一致”而全部栅格化。

八、模型配置：密钥只保存在当前设备

第一次进入系统后，需要在“模型配置”页面填写兼容 OpenAI API 的服务地址、API Key 和模型名称，并先执行连接测试。不同服务对视觉输入、结构化输出、模型列表和超时策略的支持不同，建议先生成少量页面确认效果，再开始较长任务。

九、完整用法：从新建项目到最终交付

1. 创建演示项目

填写演示主题、目标受众、沟通目的、预计时长、语言和视觉要求。这里的信息会直接影响大纲结构和页面密度，最好写清楚“观众听完以后应该理解什么或做什么”。

2. 上传并检查材料

上传 Word、PDF、Excel、旧 PPTX、Markdown、网页或图片。材料解析完成后，先检查章节、表格、数字、图片和提示信息。扫描版 PDF 或复杂公式如果没有被正确识别，应先补充可读取的文本，而不是直接继续。

3. 连接模型

在模型配置中完成连接测试。图片模型不是必需项；未配置时，系统仍可以使用材料中的图片、原生图表和基础视觉结构完成演示。

4. 生成并审阅大纲

重点检查页面顺序、论证是否完整、每页是否只有一个清晰任务，以及关键证据是否被分配到正确的位置。大纲阶段改动的成本最低，不建议跳过。

5. 生成页面候选

为页面生成候选后，比较信息层级、图文关系和阅读负担。选择最接近目标的一版，再修改文字、颜色或局部对象。已经确认的候选不会因为其他页面重生成而自动被替换。

6. 运行质量检查

处理缺失内容、文字溢出、对比度、来源、素材许可和导出兼容性问题。对于只影响单个对象的问题，优先使用定向修复，避免重新生成整页。

7. 导出并在目标软件中复核

导出 PPTX 后，应在实际使用的 PowerPoint、WPS 或 LibreOffice 中检查字体替换、换行、图表、SVG 和媒体对象。不同 Office 软件的文本度量并不完全一致，正式演示前的人工检查仍然必要。

十一、公开版本的数据与隐私边界

公开前，我重新整理了仓库边界。所有克隆实例都从空白工作区开始，不携带维护者的账号、项目数据、模型配置或个人使用习惯。

以下内容不会进入版本控制：

  • .env 与真实 API Key；
  • runtime/、数据库、日志和临时任务状态；
  • output/ 中的个人生成结果；
  • 个人经验、界面偏好和本地模型配置；
  • 内部版本记录、阶段总结和其他历史 .docx 文档。

本地运行并不自动等于满足组织级安全要求。如果把系统开放到局域网或公网，仍然需要单独配置身份认证、HTTPS、访问控制、防火墙、备份和审计。首版默认监听 127.0.0.1，不建议直接把 Uvicorn 端口暴露到公网。

十二、当前边界与这次开发的结论

映章现在已经完成了从材料上传到多格式导出的基本闭环，但它仍然是首个公开版本。

扫描版 PDF 的文字识别、复杂公式、特殊图表、第三方字体和既有 PPT 动画仍可能需要人工处理。模型也可能生成事实错误；证据绑定能够让问题更容易被发现，却不能替代最终核验。网络图片涉及的版权、商标和人物授权，也仍然由使用者确认。

这次开发让我更明确了一件事：专业演示的价值不在于一次生成了多少页面，而在于内容是否有依据、结构是否能够解释、修改是否可控，最后得到的文件是否真的能继续工作。

映章的后续开发也会围绕这条边界继续推进。首版先把材料、证据、页面和交付串成一条可靠链路，再逐步完善扫描文档处理、复杂视觉、协作审阅和 Office 兼容性。
