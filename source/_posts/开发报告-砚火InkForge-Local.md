AI 很容易续写一段文字，却很难稳定地参与一部长篇小说。

当作品进入十章、三十章甚至更长的尺度后，真正棘手的问题通常不再是“这一段写得是否流畅”，而是人物是否记得自己见过谁、伏笔是否按计划推进、角色关系有没有无故跳变、早期设定修改后后续记忆是否仍然可信，以及一次生成失败会不会让几小时的工作全部重来。

这也是我开发 **砚火（InkForge Local）** 的出发点：它不是一个只有输入框和“续写”按钮的网页，而是一套面向中文长篇与同人创作的本地 AI 写作工作台。它希望让模型真正进入“灵感—规划—拆章—写作—审校—修订—记忆”的完整生产流程，同时把作品方向和最终决定权留在作者手中。

## 为什么普通的 AI 对话难以完成长篇小说

对话式写作工具最常见的做法，是把人物卡、大纲、前文和写作要求一起放入上下文，然后让模型继续生成。短篇或单场景写作中，这种方法往往足够有效；但在长篇项目里，它会迅速暴露出几个结构性问题。

首先，上下文并不等于记忆。模型看见了一段资料，不代表它能够区分永久设定、人物当前状态、未经证实的推断和已经失效的旧信息。其次，完整作品不可能永远塞进一次请求。简单裁剪又很容易丢掉真正影响当前章节的事实。再次，模型输出本身并不可靠：它可能生成残缺 JSON、重复前文、虚构人物知情，或者在请求中断后留下一个无法判断是否完成的状态。

更重要的是，小说不是一次性生成品。作者会反复修改前文、调整人物动机、推翻某条支线。写作系统必须知道哪些记忆由哪一章正文产生，并在正文改变后让相关派生状态失效。否则，“长期记忆”反而会成为错误扩散的来源。

因此，InkForge 的核心问题不是“怎样多塞一些提示词”，而是怎样建立一套可以追踪、验证、恢复和修订的创作系统。

## 从灵感开始，由 AI 协助完成整本书的生产流程

InkForge 把小说生产拆成几个彼此衔接的阶段。

### 1. 灵感孵化

用户只需要输入一句人物设想、一个冲突或一个场景片段，AI 会扩展出两套完整但方向不同的开书方案。方案包括作品定位、核心人物、世界规则、主题命题、主要冲突和长篇故事发动机。作者比较并确认方向后，再创建为正式作品，原有作品不会被悄悄覆盖。

### 2. 全书与分卷规划

系统先确定整部作品“为什么发生变化”，再处理每一卷“必须发生什么”，最后拆解到每一章的目标、阻力、转折和章末变化。规划不是一串孤立的剧情点，而是具有因果关系和阶段职责的导演蓝图。

对于不希望被固定模板限制的作品，系统提供因果与人物、悬疑、关系、冒险、观察和自定义等叙事策略；同时保留经典的十二岗位规划模式，适合需要严格结构分工的项目。

### 3. 批量建章与逐章创作

全书规划可以批量生成章节路线，章节再被细化为场景级执行计划。每次正文生成都会组合当前章之前的可信事实、人物状态、关系、时间线、伏笔、世界书、作者偏好和相关旧正文，而不是把整本小说无差别塞进提示词。

生成结果先进入候选稿。作者可以比较、局部采用、继续修改或完全放弃。只有明确接纳后，正文才会写入作品并进入后续记忆结算流程。

### 4. 审校、精修与长期记忆

InkForge 会检查长度、截断、重复原文、循环措辞、AI 套话、现代术语、人物知情、关系变化、道具、伤势、位置、时间和世界规则。AI 自动精修可以逐章执行审校、修订、重新审校、硬规则扫描和记忆更新。

如果某章没有达到目标质量，候选稿会保留在检查点中，不会覆盖原正文。自动创作和自动精修任务都支持暂停与恢复；即使关闭浏览器，本地服务仍会保存任务进度，重新打开后可以继续。

## 让长篇不跑偏：事实、证据与时间边界

InkForge 的项目 JSON 是作品事实源，SQLite 负责事务、版本、后台任务和可重建检索索引。模型输出不能直接成为权威事实，只能形成候选内容或带证据的派生状态。

每一条人物状态、知情、关系、时间线和伏笔更新，都必须绑定到已经接纳的正文证据。系统会记录正文哈希：同一正文重复结算不会制造重复事实；正文改变后，旧记忆提交会被拒绝，受影响章节之后的派生状态也会被标记为需要重建。

这种设计尤其适合长篇修改。假设作者重写了第五章中一次关键会面，那么依赖旧版本的后续人物知情与关系状态不应该继续被当作真相。InkForge 会保留正文，但隔离不再可信的旧派生状态，并提示从受影响章节开始按顺序重新结算。

检索同样遵守时间边界。生成第十章时，系统不会注入第十一章之后才发生的动态状态；人物“作者层真相”、读者已经看到的信息，以及角色有证据知道的信息也会分开编译。这能显著减少未来信息泄漏和角色凭空知情。

## 同人创作中的 Canon Lock

同人作品除了连续性，还要面对角色 OOC 和原作资料可信度问题。

InkForge 可以为原作角色建立 Canon Profile，保存原作、时间节点、人格、价值观、能力限制、语言模式、行为模式、情绪模式和禁止 OOC 清单。上传的原作资料可以由 AI 生成待核对档案，但只有作者确认后，它才会成为高优先级约束。

正文接受前可以运行 Canon Gate，检查角色是否出现明显性格偏移、无铺垫关系突变或高风险样文复刻。资料结论保留来源与证据，模型推断不会因为写得像真的，就自动升级成原作事实。

## 一个模型或两个模型，由用户决定

InkForge 不再使用容易混淆的“单模型 GLM”“双模型 GLM”等概念。界面只提供清晰的两种选择：使用一个模型，或使用两个模型。

模型 1 通常负责正文、续写和修订；模型 2 通常负责规划、审计和信息提取。两边都配置有效 Key 时，系统自动分工；如果只填写一个 Key，全部任务会自动交给可用模型。每个位置都可以独立选择智谱、ModelScope、本地 llama.cpp，或任意 OpenAI-Compatible 服务。

这意味着作者可以用同一个模型完成全部工作，也可以把擅长文学表达的模型用于正文，把擅长结构化推理的模型用于规划。模型可以更换，但人物、世界观、Canon、知识图谱和章节记忆不会随 Provider 一起丢失。

## v0.33.1：从功能原型到工程化项目

这次重构的重点不仅是增加功能，更是让项目具备长期维护和可靠发布的基础。

后端现在采用明确的分层架构：API 层负责请求契约与状态码，领域层保存无 I/O 的故事规则，服务层编排模型工作流，基础设施层负责 SQLite、检索、凭据和备份，统一入口负责服务进程、日志、端口和健康检查。前端也按项目状态、生成、规划、资料、审校、治理、自动导演和场景工具拆分，避免所有逻辑堆在一个脚本中。

保存操作使用乐观并发控制。另一个窗口或后台任务更新作品后，旧页面不能静默覆盖新版本，而会提示重新加载或导出副本。模型调用只记录任务、耗时、重试和 token 统计，不保存正文、提示词、接口地址和密钥。

模型 Key 与作品数据库分离：Windows 上使用当前用户的 DPAPI 加密写盘，不进入项目历史、JSON 导出或作品备份。SQLite 使用 WAL 和写入等待保护，自动备份跟随应用生命周期运行。恢复备份前会创建当前数据库安全快照，校验或恢复失败时自动回滚。

## 真正面向普通用户的 Windows 部署

源码项目如果只能由开发者安装依赖，就很难成为真正可用的创作工具。因此 v0.33.1 同时提供自动部署版和便携版。

普通 Windows 用户可以下载 `InkForge-Deploy-0.33.1-win64.zip`，解压后双击 `InkForgeLauncher.exe`。启动器会检查运行环境，缺失时从固定的 Python 官方地址下载并校验安装包，再建立与应用版本、依赖指纹绑定的隔离环境。环境准备完成后会自动启动服务并打开工作台，以后启动会直接复用缓存。

便携版包含完整运行目录，适合离线保存或固定环境部署。两种发行方式都会把作品、凭据、日志和备份保存在当前用户的数据目录中，因此更新或重新解压程序不会覆盖小说。

## 测试与质量保障

一次成功启动并不能证明长篇系统可靠。当前版本建立了覆盖领域规则、项目版本、数据恢复、任务检查点、模型传输、静态资源和工程契约的自动化测试。

v0.33.1 已通过 69 项自动化测试、13 项离线质量评估和 11 个前端脚本语法检查。GitHub Actions 在 Windows 与 Linux、Python 3.10 与 3.12 的组合上执行编译、项目契约、Ruff、测试、离线评估和静态资源检查。

对于真实模型，还提供隔离的验收运行器，可以验证单模型、双模型、连续多章生成，以及服务被强制终止后的检查点恢复。真实调用结果和日志会写入隔离目录，并自动清除密钥等敏感信息。

当然，自动测试不能判断一部小说是否真正动人。它能做的是守住工程底线：正文不能莫名丢失，任务必须能够恢复，事实需要证据，未来信息不能提前泄漏，模型异常不能悄悄破坏已确认内容。文学判断依然属于作者。

## 如何开始使用

1. 打开 [GitHub Releases](https://github.com/star031104/inkforge-local/releases/latest)。
2. Windows 用户下载自动部署包并解压。
3. 双击 `InkForgeLauncher.exe`，等待首次环境准备完成。
4. 打开右上角“模型设置”，配置一个或两个模型。
5. 从一句灵感开始孵化，也可以创建空白作品后手动规划。

开发者也可以直接运行源码：

```powershell
git clone https://github.com/star031104/inkforge-local.git
cd inkforge-local
.\run.bat
```

启动后访问 `http://127.0.0.1:7860`。

## 接下来还会继续做什么

InkForge 当前已经具备从灵感到全文、从候选稿到审校精修、从章节证据到长期记忆的完整闭环。后续改进仍会围绕三个方向展开：更准确的上下文选择、更透明的自动创作过程，以及更低门槛的本地部署体验。

我始终认为，AI 写作工具真正值得投入的部分，不是让模型替作者制造更多文字，而是帮助作者管理一部作品长期累积的复杂性：人物为什么做出这个选择，某条事实从哪里来，谁在什么时候知道了什么，以及一次修改会影响到哪里。
